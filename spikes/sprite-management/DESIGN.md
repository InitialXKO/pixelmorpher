# 精灵多了之后如何管理 — 调研与纵切

分支 research/sprite-management。四个问题：①多起来
怎么管理；②UI 如何呈现；③要不要公用选择器界面；
④左侧精灵列表要不要从文字改成缩略图。

## 一、盘点（现状实锤）

**量级**：精灵的主要增量来自 3D 烘焙与拆分——一个角
色按节点 × 方向生成（塞尔凯特 29 节点 × 最多 8 方向
≈ 上限 232 张/角色），外加手绘与导入。百张级是常态，
不是极端情况。

**数据模型**：`Sprite` 只有 name 一个组织维度，没有
文件夹、标签、创建时间。引用关系不在精灵身上，靠反
查服装件（左侧删除确认已有 `countSpriteRefs` 深走统
计）。

**左侧精灵列表**（PuppetAssetPanel）：纯文字行（灰色
小方块占位，不是真缩略图）+ 名字 + 尺寸 + 特征点计
数；容器 max-h-32 ≈ 7 行可见；无搜索、无分组、无排
序；全量渲染无虚拟化；右键菜单齐全（编辑/重命名/
复制/旋转/镜像/删除带引用计数确认）；选中后下方有
属性区（锚点等）。

**选择面三套互不相通**：
1. DressPanel 方向配图：内嵌缩略图网格——全仓唯一
   可视化选择器。它的 `SpriteThumbnail` 是本地组件：
   每次挂载逐像素 fillRect 重画、无缓存，CSS 把画布
   拉成正方形（非正方形精灵变形）；选择器全量渲染，
   200 张 64×64 精灵打开一次 ≈ 80 万次 fillRect。
2. SkeletonPanel 骨骼绑定：只有 {id, name} 的文字
   名单。
3. 左侧列表本身：点行进像素编辑，是「管理面」不是
   「选择面」，但用户找精灵时最先看它。

## 二、已落纵切（本 PR）

- `src/lib/sprite-thumb.ts`：`thumbFitRect`（方框内等
  比适配居中——治变形）；`getSpriteThumbCanvas`（离
  屏画布一次栅格化，按精灵**对象身份** WeakMap 缓
  存：store 不可变更新换对象即失效，旧条目随回收；
  缓存边长封顶 96）；`filterSpritesByQuery`（名字子
  串过滤，列表与选择器共用）。
- `SpriteThumb` 共用组件：恒正方形盒、等比居中、重
  复挂载只剩一次 drawImage。
- `SpritePicker` 共用选择器组件：搜索框 + 缩略图网
  格 + 选中高亮，留 `groupBy` 分组扩展口。
- 接线：DressPanel 选择器与方向槽位图换 SpritePicker/
  SpriteThumb，本地 SpriteThumbnail 删除；左侧列表行
  内换 18px 真缩略图 + 列表顶部加搜索框。

## 三、四问的选项（待用户定）

**Q1 管理模型（组织维度）**
- 说法甲：不加数据字段，**派生分组**——按引用状态
  （已被槽位引用/未引用）、按来源（属于哪个角色的
  烘焙批次）自动分组，零迁移、零维护负担；缺点是分
  组口径由系统定，用户不能自定义归档。
- 说法乙：给 Sprite 加 `folder`（单层文件夹名字符
  串），用户手动归档；缺点是多一份要维护的元数据，
  批量生成时文件夹归属要定缺省规则。
- 说法丙：给 Sprite 加 `tags` 数组，多标签过滤；比
  文件夹灵活，缺点同乙且标签词表容易发散。

**Q2 呈现形态**
- 说法甲：左侧保持**列表**形态（缩略图小图 + 名字
  + 搜索），管「找与管」；选择走弹层/内嵌网格，管
  「挑」。两种形态分工。
- 说法乙：左侧改**资产网格**（双列缩略图墙），与选
  择器同形态；代价是左栏宽度下每行张数少、名字显
  示空间被挤，节点树等其他段落的纵向空间要重排。

**Q3 公用选择器**
- 说法甲：一个共用组件，多形态（内嵌与弹层同体），
  全部调用面（DressPanel 已迁、SkeletonPanel 待迁）
  统一到它；搜索/分组/缩略图只维护一份。
- 说法乙：只共用缩略图与过滤逻辑（本 PR 的库层），
  容器与布局各调用面按场景自理；灵活但交互口径会
  慢慢分叉（现状即如此长成三套）。

**Q4 左侧列表缩略图**
- 说法甲：行内小缩略图 + 名字并存（本 PR 已落）：
  扫图快、名字可搜索可读，行高从约 18px 涨到约
  24px，同屏行数略减。
- 说法乙：纯缩略图（无名、悬停显名）：密度最高，
  但同名/近名精灵（烘焙产物常同前缀）无法只靠图
  区分，且失去文字扫读。

## 四、各方案优劣分析（2026-10-26 应用户要求补）

先摆一条贯穿四问的事实：这批精灵的主力是**机器生
成**的——烘焙 id 形如 `spr_<角色>_<骨序>_<方向>`，
同部件的 8 个方向图轮廓几乎一样、靠名字（骨名+方
向）区分彼此。凡是「靠图认精灵」的方案，都要先过这
一关。

**Q1 管理模型**
- 甲（派生分组）：零数据改动、零维护。能派生的最
  有价值的一维是**引用状态**——「未被任何槽位引
  用」直接支撑清理积压的烘焙废图（现行删除确认已
  在逐个反查引用数，口径现成）。短板：分组口径系
  统说了算，表达不了「武器/特效」这类用户意图；
  且精灵表是全工程共用的，一张图可被多角色引用，
  「按来源分组」天然多归属，分组会重叠。
- 乙（folder 字段）：心智最熟、实现最轻（一可选字
  段 + 按夹过滤）。短板在生成侧：烘焙/导入一次生
  成上百张，缺省落哪个夹必须定规则（按角色名自动
  建夹是最自然的缺省，但那样它就退化成甲的「按来
  源」加一层可改名）；用户不整理时全堆根目录，文
  件夹制就名存实亡——它的成败不在 UI，在生成侧缺
  省规则和用户整理习惯这两件不可控的事上。
- 丙（tags）：唯一能多维的（来源+部位+用途同时
  在）。自动打标空间也最大：生成时按角色/骨名/方
  向自动上标，用户只补用途标——这能把乙的「缺省
  规则」问题一并吃掉。短板：标签词表会发散（同义
  词、大小写、中英混写），需要词表治理（已有标签
  提示/改名合并）；打标 UI（批量选、批量上标）比
  文件夹的拖放归档更费工。
- 分水岭：管理的主要痛点是**清理废图**还是**按用
  途找图**。前者甲就够（引用状态是派生的、永远准
  确）；后者必须有用户维度，乙/丙之间选——丙的自
  动打标能覆盖乙的大部分场景，乙只赢在心智简单。

**Q2 呈现形态**
- 甲（列表管找管、网格管挑）：两种形态各自长在合
  适的容器里——左栏窄（约 260px）且与角色/节点/
  插槽等段落共存，列表能同屏放下名字全长+尺寸+
  引用状态；选择器是临时面、可用宽度大，网格扫图
  快。本 PR 已按这个方向接了两面，迁移风险最低。
- 乙（左侧改网格）：资产浏览的直觉最强，找「一张
  眼熟的图」最快。代价：260px 宽只放得下 2 列，
  烘焙长名字（角色_部位_方向）必然截断，而截断掉
  的恰是区分方向的后缀；尺寸/引用数等管理信息没
  地方放；左栏其他段落的纵向空间要整体重排，改
  动面远大于精灵段本身。
- 分水岭：左侧列表的日常动作是「按名字定位一张」
  还是「扫图认一张」。烘焙命名规律决定了前者占
  多数；手绘精灵为主的工程则相反。

**Q3 公用选择器**
- 甲（一组件多形态全迁）：交互口径只一份，搜索/
  分组/性能优化落一处全仓受益；现状三套分叉就是
  没有公用件的自然结果，放着不管还会继续分叉。
  代价：调用面场景不同——穿衣是逐方向配图（网格
  合适），骨骼绑定是窄面板里的单选（网格塞不下、
  需要列表密度形态），组件要出 grid/list 两形态，
  接口要照顾「选完即关」与「常驻切换」两种节奏。
- 乙（只共用库层）：本 PR 已落的形态，改动最小、
  各面保留贴合场景的容器。短板：统一只到「画得对
  不对、快不快」，到不了「长得一样不一样」；下次
  哪个面要加搜索/分组，还得各加各的。
- 分水岭：愿不愿意为骨骼绑定这类窄面做列表形态。
  愿意，甲成立且一劳永逸；不愿意，乙是诚实的停
  点，但要接受口径继续分叉。

**Q4 左侧缩略图**
- 甲（18px 小图+名字，本 PR 已落）：严格优于原来
  的灰方块占位——能辨部位轮廓、名字可读可搜。短
  板是容器：行高涨了之后 max-h-32 只剩约 5 行可
  见，**真正卡脖子的是列表高度不是缩略图**，这条
  无论甲乙都得单独处理（段落可拉高/独立滚动区）。
- 乙（纯缩略图）：密度最高，但对这批资产是错的
  工具——同部件 8 方向图轮廓近乎一致，区分全靠
  名字；去掉名字等于把最常用的区分维度扔掉，只
  靠悬停提示逐张试。乙只在「图与图长得明显不同」
  的资产结构（手绘图标类）下成立。
- 这一问证据最单边：甲。乙的合理形态其实是 Q2
  的乙（整面网格墙），不该在列表行里实现。

## 五、未决与后续

- Q1–Q4 待用户定；定了 Q1 才动分组接线（SpritePicker
  的 groupBy 已留口，派生分组可先行，folder/tags 需
  动数据模型与导入/烘焙的缺省归属）。
- SkeletonPanel 骨骼绑定的精灵选择未迁（等 Q3 定）。
- 虚拟化未做：缓存后单张成本只剩 drawImage，300 张
  内全量渲染可接受；若工程量级到千张再上虚拟滚动。
- 真机未验：缩略图在真实工程里的辨识度与滚动跟手。
